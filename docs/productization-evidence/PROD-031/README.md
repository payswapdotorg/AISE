## The design, in one page

**The selection ladder (the surface's mount discipline).** The solution
surface (`apps/web/src/app/surfaces/Solution.tsx`) mounts its workspace
through a three-rung ladder, each rung honest about its own failure:

1. **Rung 1 — the local engine mount.** A lazy import of the local engine
   binding (`service.ts`, which imports `@aise/solution-engine` directly).
   In Node contexts this runs the engine in-process. In a plain browser the
   engine barrel's transitive `node:crypto` dependency externalizes and
   throws at call time — the rung logs its outcome
   (`[solution-surface] rung 1 … falling to the browser mount`) and the
   ladder falls through. **Never a crash, never a silent skip.**
2. **Rung 2 — the browser mount** (`apps/web/src/app/solution-browser-mount.tsx`).
   A crypto-free composition: the same surface, the same engine law, but the
   workspace executes through the backend's live routes over the HTTP
   service seam (`createHttpSolutionService`) and the agent port
   (`createHttpSolutionAgentPort`). The opening leg (the baseline
   materialization) and the engine binding set are cached OUTSIDE render —
   one `WeakMap` per fetch transport / per service instance — because
   React's `use()` law discards a suspended render's hook state, and a
   render-created promise or `useMemo` binding re-fires the baseline POST
   forever (the defect the pre-closeout console evidence captured; fixed in
   `605d86d`).
3. **The honest panel.** If both rungs fail, the engine-unavailable
   composition renders (an explicit `#solution-engine-unavailable`
   section), still zero page errors.

**The port map (what the browser actually calls).** All calls are
same-origin `POST`s over the app's gated fetch (the demo session's cookie
rides it; no configurable origin — the PROD-001 contract):

| Port | Routes | Purpose |
| --- | --- | --- |
| The solution service seam (`service-http.ts` → `handleSolutionRequest`) | `POST /v1/solutions/step \| validate \| inspect \| quantities \| revise \| baseline` | the engine's operations: step (submit an operation), validate (the deterministic checks), inspect (a proposed state), quantities (measurement), revise (the serializable revision leg), baseline (the layer-0 materialization — the browser mount's opening leg) |
| The solution agent port (`agent/port.ts` → the PROD-023 compiler) | `POST /v1/solution-agent/compile \| turn` | the NL→intent compiler + its clarification/proposal loop; the workspace never re-implements the compiler |

**The `@aise/solution-contract/browser` subpath (the crypto-free cut).**
`packages/solution-contract` now exports `"./browser"` → `src/browser.ts`
(the PROD-030 pattern): the wire objects and contract logic the BROWSER
graph needs, with no transitive `node:crypto`. The crypto-freeness is not
asserted by review but **proved by the gate**: `tools/web-bundle/gate.ts`'s
`scanBrowserGraphForCryptoMarkers` scans every built asset for Node-builtin
externalization markers, and the browser-journey test asserts the finding
list is empty (the only excused asset is the documented legacy local-engine
mount chunk, ≤ 1). Commit `882896d`.

**The committed journey record + parity test.** The browser mount renders
its BOQ from ONE committed record —
`apps/web/src/app/solution-journey-record.json` (generated by
`solution-journey-record.generate.ts`, the §4.6 "one record" choice: pure
data over the frozen world pins, never re-derived per render). The parity
test `apps/web/src/app/solution-journey-record.test.ts` pins it four ways:
(1) it deep-equals a LIVE Node run of the one runner (no drift, no second
record), (2) its canonical serialization round-trips losslessly, (3) the
committed file is the generator's byte-exact output shape, (4) it carries
the committed demo world pins and the twelve-step journey shape.

## The gate and its extension

`tools/web-bundle/gate.ts` is the web-bundle gate's shared machinery,
extended for PROD-031 with the local deployment stack:
`buildWebAppOnce` (the vite build, memoized), `startLocalDeploymentStack`
(a loopback backend child — `bun run start` with the inherited
`DATABASE_URL` stripped, so the gate never needs a live Postgres — plus a
same-origin proxy serving the built bundle and forwarding `/healthz`,
`/readyz`, `/v1/*`), `chromiumExecutable`, `browserMountAssets` /
`legacyEngineMountAssets` (the mount-chunk sentinels) and
`scanBrowserGraphForCryptoMarkers`. `solution-journey.test.ts` (NEW) is the
§6 browser-journey gate over that machinery; the pre-existing
`check.test.ts` remains the PROD-030 web-bundle gate.
