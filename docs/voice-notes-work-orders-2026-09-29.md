## VOICE-002 — Voice-note capture in the web Capture surface (the client lane over the VOICE-001 contract)

**Protected primary surfaces:** `apps/web/src/app/surfaces/CaptureMission.tsx` (the Capture/Upload surface — `CaptureUploadPanel` / `CaptureUploadCardBody` / `EvidenceRegistrationPanel`; ADDITIVE work only: the stills/video upload + registration flow must not change behavior), `apps/web/src/app/evidence-registration.ts` (the registration draft's pure logic — the closed vocabulary mirror `EVIDENCE_ACQUISITION_METHODS` stays pinned to `EVIDENCE_METHODS` verbatim, test-enforced; the voice keys extend the draft → wire-body mapping, never the vocabulary), and `apps/web/src/app/api.ts` (the live client functions — additive only; the voice read seam is a NEW function, never a signature change to `uploadCaptureAssetLive` / `registerEvidenceLive` / `loadEvidenceIndexLive`). READ-ONLY for this work order (client-only, by design): everything under `backend/` — the contract and its conformance suite are done and green; in particular the `AsrProvider` seam (`backend/api/src/evidence/transcription.ts`) must NOT be wired, unwired or altered; everything under `packages/shared-contracts/` — `1.1.0` is frozen; everything under `apps/android/` — the field-capture follow-up owns it.

### Objective

A field voice note enters as evidence through the web Capture surface exactly like every other evidence kind: file-based audio upload (`accept="audio/*"`) through the same file-input → Web-Crypto sha-256 digest → `POST /v1/capture/assets/:contentId` → server-validated registration (`POST /v1/evidence`, `acquisitionMethod: "VOICE_NOTE"`) flow the stills/video lanes use — with the VOICE-001 voice acquisition metadata surfaced honestly (only what the client can actually know, never fabricated) and the transcript state rendered per the contract's honest-degradation semantics: with no ASR provider configured the voice note registers and the UI shows the explicit no-transcript state (`asr_provider_not_configured`) — never a fabricated transcript, never an error.

### Required work

- The voice-note acquisition lane: the Capture surface gains a file-based audio upload entry accepting `audio/*` — the same file-input → digest → upload → register flow as stills. Reuse the existing seams unchanged: `webCryptoSha256()` (the TRANSPORT content address — the gateway re-verifies server-side) and `uploadCaptureAssetLive()`; the capture gateway is already media-type-agnostic (VOICE-001's own conformance uploaded `audio/ogg` through it). A dedicated audio-accepting entry (`accept="audio/*"` on the file input) is the instructed minimum; a single entry with honest audio detection on selection is acceptable only if the voice metadata lane still renders identically — the worker picks per the existing surface patterns, and the demo-mode / Web-Crypto-unavailable / typed-failure explicit states must hold for the voice lane exactly as they do for stills.
- Voice acquisition metadata — honest, per the contract header (`packages/shared-contracts/src/evidence.ts`): the canonical keys are `voice.duration.ms`, `voice.codec`, `voice.sample.rate.hz`, `voice.language.hint` (all string values; numeric values string-encoded integers — see the fixture `packages/shared-contracts/fixtures/evidence/Evidence.valid-voice-note.json`). The lane displays and registers ONLY what the client can actually know:
  - `voice.codec` — the media subtype of the browser-reported media type (what the `File` object itself states, e.g. `ogg` for `audio/ogg`). The contract's own example value `opus` is a field device that knows its encoder; the browser lane reports the weaker claim it can actually observe — never a guessed codec behind a container.
  - `voice.duration.ms` — measured client-side when the platform can measure it (e.g. `HTMLMediaElement` metadata); honestly absent when it cannot.
  - `voice.sample.rate.hz` — measured client-side when the platform can decode it (e.g. Web Audio `decodeAudioData` → `AudioBuffer.sampleRate`); honestly absent when it cannot.
  - `voice.language.hint` — an OPTIONAL user-entered hint (advisory only per the contract header — a hint for ASR providers and UIs, never an authoritative language determination); absent by default.
  - The lane may additionally set the well-known `capture.kind` to `"voice"` (the operator chose the voice lane — a fact, not an inference).
  Absence renders as absence — never zero, never "unknown", never fabricated (the open-map discipline: unmeasured keys are simply not asserted).
- Registration uses the EXACT VOICE-001 contract: the wire body stays the exact Evidence document (`contractVersion` pinned to the shared `CONTRACT_VERSION` constant — never a literal; `acquisitionMethod: "VOICE_NOTE"`, which is already the honest prefill for `audio/*` via `defaultAcquisitionMethod` — keep it) with the voice keys riding `acquisitionMetadata` alongside the existing `session.id` well-known key. Extend the `evidenceRegistrationRequestBody` draft → body mapping (and its named-defect validation) for the voice lane; do not fork a second registration path. The pinning gate applies as for every kind: the audio bytes must be uploaded before registration, and a `content_not_pinned` refusal surfaces verbatim.
- The transcript state — honest per the contract, client-only. Add a client read function for `GET /v1/evidence/:contentId` (the read view already answers `derivations: { inputsOf, derivedFrom }` — pinned by VOICE-001's conformance) and derive the state from it:
  - no `transcription.asr` entry in `inputsOf` → the explicit NO-TRANSCRIPT state with reason `asr_provider_not_configured` (the deployment's actual state — no ASR provider is configured; the reason word is the contract's own vocabulary) — a calm informational state: never an error, never a fabricated transcript, never a silent skip;
  - a `transcription.asr` entry present (the future provider-configured path) → the transcript derivation outcome + its provenance link render: the method identity, `methodVersion` (the ASR engine/model identity), the `outputContentId` of the content-addressed transcript artifact, and the `DERIVED_FROM` linkage — presented as a DERIVED CANDIDATE, never authoritative text, never a rewrite of the raw evidence.
  Design for BOTH states; prove the no-provider path (that is the deployment's live state). Do NOT add a backend transcript-state route — VOICE-001 deliberately did not add one and this work order adds none (backend is out of scope); the client derives the state from the read view's own derivations set, which is inspectable today.
- Evidence lists — voice notes like any other evidence kind: the SiteTwin evidence card (and the other evidence surfaces rendering `acquisitionMethod`) show a kind badge — kebab-case, `voice-note` for `VOICE_NOTE` (e.g. `still-imagery`, `video-footage`, `voice-note` from the same mapping; the presentation follows the existing tag patterns). Voice notes are not a special case: every kind renders the same badge discipline.
- Tests — the `capture-mission.test.tsx` discipline (static renders of pure projections via `renderToStaticMarkup` + typed seam tests with stubbed transports):
  - the upload+register flow: audio file selection renders the honest metadata display (measured keys shown, unmeasured keys absent — never fabricated), and the registration body carries `VOICE_NOTE` + the canonical voice keys with string values (string-encoded integers for numerics) — checked against the contract fixtures;
  - the honest no-transcript state: a registered voice note with an empty derivations set renders the explicit `asr_provider_not_configured` state (no error, no transcript), and a provider-configured fixture (a `transcription.asr` derivation in `inputsOf`) renders the derivation outcome + provenance link;
  - the kind badge: `voice-note` renders for VOICE_NOTE evidence on the evidence lists;
  - the existing stills/video upload + registration tests stay green and unmodified (regression).
- Typecheck + the full gate: `bun run verify` PASSES at the delivered tree.
